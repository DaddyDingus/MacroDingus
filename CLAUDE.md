# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

macrotrack is a personal nutrition/macro tracking PWA (MacroFactor-style), built for a single household running it on their own homelab server — not a public multi-tenant SaaS. Backend and frontend are separate npm packages in one repo; there is no root `package.json`.

## Commands

Backend (`backend/`):
```
npm run dev     # tsx watch src/index.ts — hot-reloading dev server on :3000
npm run build   # tsc -p tsconfig.json, then copies src/db/migrations into dist/
npm run start   # node dist/index.js — runs the built output
```

Frontend (`frontend/`):
```
npm run dev       # vite dev server; proxies /api to http://localhost:3000 (see vite.config.ts)
npm run build     # tsc -b && vite build
npm run preview   # preview the production build locally
```

There is no lint script and no test suite in either package — don't invent one. Type-check with each package's `build` command (or `npx tsc --noEmit` from within `frontend/` or `backend/`).

Local dev requires both dev servers running at once (backend on :3000, frontend on its Vite port proxying to it). `better-sqlite3` and `bcrypt` are native modules — installing `backend/`'s dependencies on the host needs a C toolchain (`python3 make g++`); if that's unavailable, build via Docker instead (see below), which installs the toolchain inside the `backend-build` stage.

Production is a single multi-stage `Dockerfile` (frontend build → backend build → runtime) producing one container that serves the API and the built static frontend from the same Fastify process/origin — deployed via `docker compose build && docker compose up -d` in this directory. `DATA_DIR` (default `../data` relative to the backend) controls where the SQLite file, cookie secret, and uploaded photos live; point it at a scratch directory for any throwaway/test runs so you never touch the real database.

**After any code change the user should be able to see or use, redeploy the live container** — `docker compose build && docker compose up -d` in this directory, then a quick sanity check (`docker ps` shows a fresh `Up X seconds`, `curl .../api/health`). This is a separate step from committing/pushing to git and separate from verifying against a scratch container (copy `data/` elsewhere, run a throwaway container from the built image bound to `127.0.0.1`, never touch the live container/data while iterating) — scratch-container testing confirms correctness without any risk to real data, but it does not update what's actually running. Skipping the redeploy step after a real change means the user's phone keeps showing the old build no matter how hard they refresh; this has actually happened (a full dashboard rebuild was committed and pushed while the live container still ran a 14-hour-old image).

## Architecture

**Data model** (`backend/src/db/schema.ts`, Drizzle ORM + `better-sqlite3`, migrations in `backend/src/db/migrations/` via `drizzle-kit`): `users`, `foods` (shared across all users), `recipes` + `recipe_ingredients`, `logs`, `weights`, `profiles`, `checkins`, `photos`. Two things shape most of the routes and are easy to miss from a single file:

- **A recipe is not a separate loggable entity.** Creating/editing a recipe materializes a normal `foods` row (`source: 'recipe'`) computed from its ingredients — `caloriesPer100g` etc. derived from the ingredient sum, `servingSizeGrams = totalWeightGrams / servings`. Logging a recipe is then just logging any other food; there is no recipe-specific branch anywhere in the log-entry path. `totalWeightGrams` is stored independently of the ingredient weight sum because cooking changes weight (water loss/gain) without changing total calories.
- **Foods are shared, everything else is per-user.** `foods` has no `userId`; `logs`, `weights`, `profiles`, `checkins`, `photos`, and recipe *metadata* (not the resulting food) all do. A barcode lookup or custom food created by one person is immediately available to everyone on the instance.
- **`profiles` also carries goal-progress state**: `goalWeightKg` (nullable — a goal is optional) plus a snapshot pair `goalStartedAt`/`goalStartWeightKg` captured in `POST /api/profile` at the moment `goalWeightKg` is first set or changed (not on every profile save — compared against the previously-stored value). This is what lets the Goal Progress tile show "% of the way there" relative to the *specific* goal currently in effect rather than a stale first-ever weigh-in from a goal that's since changed.
- **Logs have no `meal` concept.** Removed entirely (not hidden — dropped from the schema) in migration `0006_open_omega_flight.sql`. `date` (the day) and `loggedAt` (a real timestamp — drives both smart-history's time-of-day ranking and the Food Log timeline's grouping, see below) are the only temporal fields left on a log row. This was a deliberate full removal, not a half-measure, so a few things that used to key off meal are gone with it: Copy-a-day lost its per-meal option (always copies the whole day now), the add-food flow's old "which meal?" step is gone everywhere it appeared (FAB menu, Dashboard shortcuts — see `QuickActionFlow.tsx`), and the edit sheet's "move to a different meal" control is gone since there's nothing left to move it to.

**Auth** (`backend/src/auth.ts`): password-only login, not username+password — `/api/auth/login` takes just `{ password }` and iterates every user running `bcrypt.compare` until one matches, signing you in as whoever's password you typed. Session is a signed httpOnly cookie (`mt_session`, 30-day expiry) containing `userId.expiryTimestamp`; the signing secret is generated once into `${DATA_DIR}/.cookie-secret` (mode 0600) unless `COOKIE_SECRET` is set. A global `preHandler` hook gates every `/api/*` route except `/api/auth/*` and `/api/health`, populating `req.userId`. Signup is self-service with no invite/approval — access control is meant to happen at the network layer (Tailscale), not the app layer.

**Coaching engine** (`backend/src/engine/tdee.ts`, `backend/src/engine/trendWeight.ts`, orchestrated by `performCheckin()` in `backend/src/routes/coach.ts`): trend weight is an EWMA (`computeTrend`, alpha=0.1) with gap correction — a longer gap since the last weigh-in pulls the trend further toward the new reading, computed by widening the effective alpha for that gap (`1-(1-alpha)^daysSinceLast`) rather than always applying a single-day step. It's recomputed from full history on every request, never stored incrementally, so backfilled/edited weigh-ins are always reflected correctly. `performCheckin()` prefers `estimateAdaptiveTdee()` (backs out real TDEE from trend-weight change vs. average logged calories over a 14-day window) and falls back to `mifflinStJeorTdee()` (a formula estimate) when there isn't yet 2+ weigh-ins and 7+ days of calorie logs to trust. A "check-in" snapshots the resulting targets into the `checkins` table — the "current" targets shown anywhere in the app are always just the latest check-in row, never recomputed live, so they stay stable day-to-day and only change when the user deliberately checks in. All date arithmetic in this engine is pure UTC (`Date.UTC`), deliberately avoiding `Date`'s local-timezone-dependent `setDate()`/`getDate()`.

**Frontend structure** (`frontend/src/`): `api/` holds one file per resource, each wrapping TanStack Query hooks around `apiFetch` (`api/client.ts`) — that's also where to look for the Content-Type-only-when-there's-a-body handling that Fastify's JSON parser requires. `screens/` are route-level components wired up in `App.tsx`; `components/` are shared pieces used across screens or composed into a screen (sheets, charts, form steps). `lib/` holds small cross-cutting concerns each following the same pattern: a React Context + localStorage-backed hook (`weightUnit.tsx`, `shortcuts.tsx`), or pure date/nutrition math with no I/O (`date.ts`, `nutrition.ts`).

Routing/bundling: `App.tsx` only keeps the Dashboard (`/`) and Food log (`/log`) screens in the eager bundle — everything else (`Strategy`, `More`, `Photos`, `dashboard/customize`, and every detail page: weight/macros/expenditure/energy-balance/goal-progress/habits-weigh-ins/habits-logging/`nutrition/:metric`) is `React.lazy`-loaded per route. Within the Dashboard itself, the bento-tile rendering is further split into its own lazy chunk (`components/DashboardTileSections.tsx`, renamed from the original `DashboardInsights.tsx`) because it's the only part of that screen touching `recharts` (~420kB); `screens/DashboardCustomizeScreen.tsx` (the "Customise dashboard" screen — its own route, not a bottom sheet) is also lazy-loaded even though it touches no chart code, purely because it's infrequently opened — don't import chart components (or other rarely-used, sizeable UI) into an eagerly-loaded screen without lazy-splitting them the same way; check the built bundle sizes (`npm run build` output) if you add one somewhere new. The barcode scanner (`@zxing/*`, ~400kB) is lazy-loaded the same way, and for the same reason it doesn't use the native `BarcodeDetector` API — that's unsupported in Firefox.

The (+) nav button and the Dashboard's 4 pinned shortcut buttons both drive the same underlying flow (`components/QuickActionFlow.tsx`) rather than duplicating the quick-add/log-weight/recipe/etc. state machine in two places — extend that one component if you add a new quick action rather than special-casing either entry point. The shortcut buttons themselves float in `components/ShortcutsBar.tsx`, a `fixed` bar just above `BottomNav`, Dashboard-only (not global chrome — the FAB already covers every other screen), hidden on scroll-down and shown on scroll-up via `lib/useHideOnScroll.ts` (rAF-throttled, small dead-zone threshold, always visible near the top). Each pinned shortcut can also carry a color (`lib/shortcuts.tsx`'s `SHORTCUT_COLOR_CATALOG`, reusing the app's existing categorical palette — no new colors introduced), picked per-shortcut from the "Edit shortcuts" checklist; a shortcut with no color falls back to the plain grey chip.

**Bottom sheets** (`components/BottomSheet.tsx`): most sheets in the app (`QuickActionsSheet`, `QuickActionFlow`'s non-food steps, `QuickAddSheet`, `CopyDaySheet`, `RecipeEditSheet`, `AddTilesSheet`) are built on this one shared component rather than each hand-rolling its own backdrop/panel/grabber div trio, which is what every one of them did before this existed. It owns the backdrop, the rounded panel, the grabber notch, and a hand-rolled swipe-to-dismiss gesture (drag the notch down past 100px, or flick it past a velocity threshold, to close) — there's no drag-and-drop library backing this or anything else in the app, deliberately (bundle size, touch-gesture reliability), so don't reach for one if you extend this. `panelClassName`/`backdropClassName` let each sheet keep its own visual identity — the older sheets are still `bg-surface`/`border-line`; newer ones (`AddTilesSheet`) are `bg-dashboardBg`/`border-white/10` — while sharing the gesture underneath. Build any new sheet on top of this rather than reintroducing the old three-div pattern. `PhotosScreen`'s photo viewer is a fixed full-bleed lightbox, not a bottom sheet, and intentionally isn't built on this. `AddFoodSheet` no longer uses this component at all — see below.

**AddFoodSheet — full-screen dual-layer modal** (`components/AddFoodSheet.tsx`, `components/DraggableSnapSheet.tsx`, `lib/quickAddPlate.tsx`): this went through several redesigns in quick succession — worth knowing they existed if you're reading old git history, since none of the earlier ones are what's live now. It started as a single `BottomSheet` with the plate+nutrition grid embedded in its own scrollable body above the mode tabs. It's now a genuinely full-screen modal (`fixed inset-x-0` sized off real visual-viewport metrics, not `BottomSheet` at all — `BottomSheet`'s one-off `transparentBackdrop` prop from an even earlier version was removed as dead weight) with a Google-Maps-style dual layer for the `"browse"` step specifically:
- **Layer 1 (background, full-screen):** the Plate View — staged items + the 2×2 nutrition grid (`StagedPlateSection`), or an empty-state message. The empty state is centered within `visibleLayer1Height` — the portion of Layer 1 actually visible above the sheet's *current* top edge (recomputed live as the sheet expands/collapses, with a matching `transition: height`) — not the full layer height and not a fixed top offset either. Centering in the full height puts it dead center of a mostly sheet-covered layer, invisible whenever the sheet is expanded (the default); a fixed top offset looks stranded once the sheet is collapsed and most of the layer is visible. Both were tried and visually disproven via screenshots before landing on the dynamic version — if you touch this, verify with an actual screenshot in both sheet states, not just one.
- **Layer 2 (foreground):** the Search/Scan/Quick Add/Custom sheet, built on a new, separate component (`DraggableSnapSheet.tsx`) rather than `BottomSheet` — it has no dismiss gesture or backdrop at all, only two snap points (expanded ≈88% of the content area, collapsed to a `SHEET_COLLAPSED_PEEK_PX` sliver showing just the tab-icon row), toggled by a chevron button in the pinned header, a drag on its own grabber, or tapping a tab while collapsed (which also re-expands and switches to it). **A real bug, now fixed:** the panel used to always render at its full expanded height and rely on `transform: translateY` alone to visually push the rest below the fold when "collapsed." That looked right, but a `position: absolute` element with `z-index: auto` always paints above plain in-flow siblings regardless of DOM order — so the panel's own opaque background, still physically hundreds of px tall, silently painted over the pinned action bar (below) whenever anything was staged, making the search input and (usually) the Log Foods button completely unclickable and invisible while collapsed. Caught via `document.elementFromPoint` returning the sheet's own (invisible, stretched) tab-row button instead of the real controls underneath, not by eyeballing a screenshot — the bug was easy to miss visually since the *empty*-plate case happened to partially still work, which is what made it look fine on a first pass. Fixed by making the panel's real CSS `height` track the snap point directly (`expanded ? panelHeight : collapsedPeek`) — `transform` is now only a live, momentary drag-feedback overlay during an active gesture, discarded the instant the finger lifts, not the mechanism collapse itself relies on. The collapsed tab-icon row is `shrink-0` with its own compact height, not `flex-1` (which used to stretch it to fill the entire — mostly off-screen — expanded-height panel, pushing the actual icons out of view too). Both the header's real rendered height and the two full-screen-modal viewport values are measured/read rather than guessed (`ResizeObserver` on the header; `useVisualViewportMetrics` for the rest), since `contentHeight = viewportHeight - headerHeight - actionBarHeight` (see below) — percentages of an unmeasured ancestor would drift under the iOS keyboard the same way `BottomSheet.tsx` already documents needing to avoid.
- **The pinned action bar** (`ActionBar`, rendered as a plain flex sibling right after the Layer 1/Layer 2 region — not a second independently `fixed`/`absolute`-positioned element, which would risk exactly the stacking fight described above) unifies the search input and "Log Foods" into one row, always in the same place regardless of tab or sheet state — replacing an earlier version where the search input was tab-specific footer content *inside* the sheet and "Log Foods" was its own absolutely-positioned floating pill elsewhere, which read as two unrelated controls that moved independently as the sheet expanded/collapsed. Its left slot shows the real search `<input>` only on the Search tab; the other tabs (this app has more logging modes than a plain search sheet, unlike what a generic "add a search bar" instruction assumes) get a same-shaped tap-to-switch-to-Search affordance instead, so the row's shape never jumps. The button itself is always rendered (disabled + "Log Foods" with no count when the plate is empty, enabled + "Log Foods (N)" once something's staged) rather than conditionally mounted, so the bar's height — measured via `ResizeObserver`, same pattern as the header — never has to be reconciled with the count changing.
- The header also grew a **staged-item avatar stack** (`FoodIconAvatar` at `w-5 h-5`, first 3 + a `+N` overflow chip) next to the chevron, so what's staged is visible even with the sheet collapsed.
- Layer 1's nutrition grid numbers are `text-base`, not `text-lg`/`text-xl` — each stat also grew a muted subtext line ("465 kcal in plate" / "83.3 g today", following the existing Plate/Day toggle) directly under it, so the big number doesn't have to double as its own unit label anymore. A "Your Plate" heading sits above the staged-items list, above the nutrition grid.
- `lib/foodEmoji.ts`'s letter-avatar fallback now matches `/[A-Za-z]/` instead of taking the food name's raw first character — a real bug (not test-data-only, though the seeded `[mock-seed]` prefix on every dev food name is what made it obvious): the first character of a bracket-prefixed or symbol-led name isn't a letter at all, so the avatar rendered the bracket itself. Matching the first actual letter is correct even against `[mock-seed] Olive oil` — it just means the seed prefix's own "m" wins over the real food name's "O", which is a property of that debug prefix, not a bug in the fix.
- The pinned header's calorie/protein "N left" budget badges (`BrowseHeader`) fold in `plateTotals`, not just the day's already-logged `totals` — they tick down live as items are staged, matching the Nutrition grid's own Plate/Day totals (which already did this) instead of silently lagging a step behind until the plate is actually committed. `BrowseHeader`'s `onClose` prop is no longer `AddFoodSheet`'s raw `onClose` — it's `requestClose`, which shows a small custom confirmation (`UnloggedPlateWarning`, styled like the app's own dialogs rather than a native `window.confirm()`) whenever the X is tapped with anything still staged, since the plate's close/reopen persistence (see above) only covers this app session — a real refresh or PWA relaunch still loses it. "Keep editing" just dismisses the warning; "Close anyway" closes normally (the plate itself is untouched either way, same as any other close).

**Staging does NOT survive closing the sheet** (X, "Close anyway" on the unlogged-plate warning, or a completed "Log Foods") — every fresh open starts from an empty plate. This is a reversal of an earlier version's explicit design (see git history), which deliberately preserved a staged-but-unlogged plate across close/reopen; that turned out not to be what was wanted in practice (opening the sheet later kept resurfacing stale items from a previous, abandoned session) and was changed on direct user feedback, not a re-litigation of the original request. The reset happens in `AddFoodSheet.tsx`'s own `useEffect` (fires whenever `open` becomes true) calling `clearPlate()` — deliberately *not* listing `clearPlate` itself in the dependency array, since `usePlateState()` returns fresh function references every render and depending on it would re-clear (and could loop) on every render rather than only on an actual open transition. `lib/quickAddPlate.tsx` is plain local state now, no Context/Provider — an earlier version had a `QuickAddPlateProvider` mounted at the app root specifically so QuickActionFlow's plate (the FAB and Dashboard shortcuts, which get fully *unmounted* by their callers on dismiss — `{runningAction && <QuickActionFlow .../>}` in `ShortcutsBar.tsx`/`QuickActionsSheet.tsx`) would survive that unmount; once every open clears the plate regardless, surviving the unmount stopped mattering (React destroys local state on unmount anyway, so a freshly remounted instance already starts empty for free) and the Context was removed as dead weight. TodayScreen's own instance and the FAB/shortcuts instance still end up with independent plates — now simply because each is its own component instance with its own local state, not because of any explicit separation mechanism.

**Food detail screen** (`components/FoodDetailScreen.tsx`): tapping a search result's row body opens this full nutrition-breakdown view instead of instantly staging — a separate "+" button on the right of each row (`aria-label="Quick add <name>"`) still stages immediately with the food's default quantity, so the original fast multi-add flow (search → tap → tap → tap → Log Foods) is unchanged; this was a deliberate hybrid, not a full replacement of instant-add, per explicit direction (MacroFactor-style: tap row = inspect, tap "+" = quick add). Both paths resolve a synthetic `off:` OpenFoodFacts search result into a real cached food first (same `barcodeLookup` cache-or-fetch call `pickFood` already used) — the detail screen especially needs this, since it reads `fiber`/`sugar`/`saturatedFat`/`sodiumMg`/`microsJson`, none of which a synthetic result carries. Quantity/unit entry uses a custom on-screen keypad (g/oz/lb/serving pills + a 12-key digit grid), not the native number keyboard, toggled open by tapping the quantity chip — deliberately not always-visible, since permanently reserving that much footer height would crowd out the scrollable breakdown content above it. The four circular "Impact on Targets" rings show this serving as a % of the *remaining* daily target (`target - alreadyConsumedToday`), not % of the full target, per spec — reuses the same `pct()` clamp-to-[0,100] helper pattern already used elsewhere, so a food that would blow the remaining budget just shows a full ring rather than overflowing past it.
  - **Breakdown sections**: Protein (single row — this app has no amino-acid-profile/protein-type data anywhere, from OFF or otherwise, so it isn't fabricated), Carb (Fiber/Sugars/Net Carbs), Fat (Saturated/Monounsaturated/Polyunsaturated/Omega-3/Omega-6/Trans/Other), **Vitamins**, **Minerals**, then Other (Sodium/Cholesterol) — Vitamins and Minerals are two separate categorized sections, not one lumped list, each independently skipped when this specific food has nothing in that category (see below) rather than showing an empty heading.
  - **Fat subtypes are real `foods` columns** (`monounsaturatedFatPer100g`/`polyunsaturatedFatPer100g`/`omega3Per100g`/`omega6Per100g`/`transFatPer100g`, migration `0007_light_eternals.sql`) — a deliberate exception to the "rare micros go in the opaque `microsJson` blob" rule schema.ts documents for vitamins/minerals: it's a small, closed set (there's no "one more fat subtype" the way there's always another obscure vitamin), and omega-3/omega-6 specifically were asked for as first-class tracked nutrients. None of the five has an FDA %DV (only Saturated Fat and Total Fat do — Trans Fat never got one; there's no safe threshold), so none of these rows gets a bar, same treatment as Net Carbs/Other Fat/Cholesterol already had.
  - **Vitamins and minerals stay in `microsJson`**, but the set fetched from OpenFoodFacts (`backend/src/engine/openfoodfacts.ts`'s `MICRO_KEYS`) grew from 11 to a full standard-label set: vitamins A/C/D/E/K/B1/B2/B3(niacin, OFF calls this field `vitamin-pp` — not a typo)/B6/B9(folate)/B12, plus calcium/iron/magnesium/potassium/zinc/phosphorus/copper/manganese/selenium/iodine, plus cholesterol (kept with the minerals-family blob even though it isn't one, per the schema comment). `FoodDetailScreen.tsx`'s `VITAMIN_META`/`MINERAL_META` mirror this list for display. Only keys actually present render — a missing field means *unreported*, not zero, so it's omitted rather than shown as a fake 0. OFF's `_100g` fields are always grams internally regardless of the unit shown on the product's own label, so display conversion to mg/mcg (×1,000 / ×1,000,000) happens in the meta tables, not just a raw pass-through — get this wrong and the numbers are actively wrong, not just missing, so double-check against a known product if you touch it (verified against a real scanned "Weetbix" row and a hand-entered custom food round-tripped through `CreateFoodForm` → API → back: both landed at the correct mg/mcg values and %DV).
  - **`CreateFoodForm.tsx` exposes all of the above as optional inputs**, not just the original fiber/sugar/sat-fat/sodium set — organized into the same category groups as the detail screen (Carbs/Fats/Vitamins/Minerals/Other) behind the existing "+ Add more nutrients" disclosure. Fat subtypes map straight to their own `CreateFoodInput` fields (already in grams, no conversion). Vitamins/minerals are entered in normal label units (mg/mcg) and converted to the grams-per-100g-equivalent storage format at submit time (`MICRO_FIELD_GROUPS`' `toGrams`), then sent as one `micros: Record<string, number>` bag — the backend's `foodInput` zod schema (`backend/src/routes/foods.ts`) accepts that bag on both `POST`/`PATCH /api/foods` and serializes it straight into the `microsJson` column (`microsJsonFromInput`), same shape OFF imports already produce, so every downstream reader (the detail screen) doesn't care which source populated it.
  - **Color-coded bars**: each breakdown section's progress bar uses that macro's own established categorical color (`bg-protein`/`bg-carbs`/`bg-fat` — same validated hex values as everywhere else macros get a color) instead of one neutral bar for everything; Vitamins, Minerals, and Other keep the neutral bar since none is one of the four established macro categories and none has its own validated color.
  - **%DV, not personal targets**: Protein/Fiber/Sugar/Saturated-Fat/Sodium/vitamin/mineral rows use FDA Nutrition-Facts-label %DV reference amounts (50g/28g/50g/20g/2300mg/etc. for a 2,000-kcal diet) as their bar denominator, clearly labeled as such — this app has no per-user target for any of those (only calories/protein/fat/carbs are tracked in `checkins`), so a personalized "% of target" the way the rings show isn't available. Net Carbs, "Other Fat," the other fat subtypes, and Cholesterol intentionally show no %/bar at all, since none is a real %DV line on an actual nutrition label and a made-up reference would be misleading.
  - A **real unit bug** existed here before this pass: Sodium was rendered with a hardcoded " g" suffix even though `Nutrition.sodiumMg` is milligrams, not grams — every sodium figure on this screen was silently off by 1000×. Fixed by adding a `unit` param to the shared row component instead of hardcoding "g".
  - A "Favorite" quick action from the original request was dropped entirely — no backend support exists for it (no column, no table, no route), and adding one wasn't in scope for what was asked. "Types of protein"/amino-acid profile was dropped for the same reason (no such data anywhere, from OFF or otherwise) and is explicitly called out as unavailable in-app rather than silently missing.
  - Deliberately **not** extended to the day-totals pipeline (`Nutrition`/`scaleNutrition`/`logs`) — these are per-food reference data (`Food` columns + `microsJson`) surfaced only on this one detail screen and the create-food form, not summed into daily totals anywhere. That would be a materially bigger feature (a real "today's vitamin C" tracker) than what was asked for, and would ripple into every screen that touches `Nutrition`.

**Dashboard tile system** (`lib/dashboardLayout.tsx`, `components/DashboardTileSections.tsx`, `screens/DashboardCustomizeScreen.tsx`, `components/AddTilesSheet.tsx`): the Dashboard is four fixed, non-reorderable categories (Insights & Analytics, Habits, Nutrition, Body Metrics), each holding bento tiles the user can individually toggle on/off and reorder *within that category*. Customizing is its own screen, not a bottom sheet, reached via the Dashboard's "Customise dashboard" tile — that screen lists only the currently-*enabled* tiles per category, each with a drag handle (`GripVertical`) for reordering; toggling a tile on/off moved out to a per-category "+ Add {category}" bottom sheet (`AddTilesSheet.tsx`), the only place the monochrome `ToggleSwitch.tsx` control appears. Reordering is a hand-rolled pointer drag (`DashboardCustomizeScreen.tsx`'s pointer handlers call `reorder(category, id, toIndex)` in `dashboardLayout.tsx` as the drag crosses into a neighboring row's slot, with the dragged row's sub-row-height remainder applied as a live `translateY` so it keeps tracking the pointer smoothly between snaps) — same "no DnD library" stance as the bottom sheets above. Persistence is one `localStorage` array of enabled tile ids per category — same Context+localStorage shape as `lib/shortcuts.tsx`/`lib/weightUnit.tsx`, no backend table. `load()` deliberately does **not** try to auto-append catalog tiles missing from a user's stored layout (an earlier version did, to handle "a tile added in a future release," but that's indistinguishable from "the user turned this off," so it silently reverted every toggle-off on reload) — a tile added to the catalog later just won't appear until the "+ Add" sheet is opened, same trade-off `shortcuts.tsx` already accepts. `lib/checkins.ts`'s `activeCheckinForDate()` (latest checkin with `date <= target`, computed client-side against the full unbounded `GET /api/checkins` history) answers "which targets were active on some past date," needed by both the Energy Balance chart and every nutrient detail page's daily history list. Any weight mutation (`useLogWeight`/`useDeleteWeight` in `api/weights.ts`) invalidates both `["weights"]` and `["coach"]` — `/coach/status` recomputes trend weight live from full weight history on every request, so a new or deleted weigh-in changes what that endpoint would return right now, but a cache invalidated only under `["weights"]` doesn't know that; miss this on a future mutation touching a live-computed endpoint and a dashboard tile reading it (Goal Progress, Expenditure) shows stale data until something unrelated forces a refetch.

**Food Log timeline** (`screens/TodayScreen.tsx`, `lib/logGrouping.ts`): blank-by-default and chronological, not meal sections. Entries are grouped for display by a rolling 30-minute window (`groupLogEntriesByTime`: an entry joins the current group if it's within 30 minutes of the *previous* entry added to that group, not the group's first entry, so a slow trickle of items each ~25 minutes apart still chains into one group while any single gap over the window always starts a new one — verified by hand against real seeded data, e.g. a run of entries at :36/:55/:56 correctly chained into one group while a same-day :08/:24/:25 pair correctly split into two). Each food is still its own `FoodLogEntryCard`; a group's entries share one timestamp, rendered as a node on a vertical line down the right edge (`lib/date.ts`'s `formatLogTime`). The old big "Today's totals" card was replaced by a sticky header (`MacroSummaryBar.tsx`) — four compact `TargetProgressBar`s (Calories/Protein/Fat/Carbs). Timestamps are pulled out of `loggedAt` via regex, never through `Date` (`formatLogTime`/`minutesBetweenLoggedAt`) — `loggedAt` is a fake-UTC ISO string that's actually local wall-clock time (see `localIsoNoTz`), so a real UTC-to-local conversion would double-shift the displayed time by the browser's timezone offset.

**Food search** (`GET /api/foods`, `backend/src/engine/openfoodfacts.ts`): the `foods` table only ever gets rows from a barcode scan, a custom entry, or a materialized recipe — there's no bulk generic food database seeded anywhere — so a plain-language search also falls back to OpenFoodFacts' name-search endpoint (`searchOffProducts`, the legacy `/cgi/search.pl` — the v2 API has no free-text search) whenever local matches are thin. Results are synthetic (`id: off:<barcode>`) until actually picked, at which point `pickFood` in `AddFoodSheet.tsx` resolves the real row through the same cache-or-fetch path a barcode scan uses. OFF's public endpoints 503 often enough under normal (not just rapid) request rates that every call to them gets one short-backoff retry (`fetchOffWithRetry`); the search input is also debounced 350ms, since typing a word used to fire one request per keystroke and hammer OFF hard enough to 503 mid-word.

The service worker (`vite-plugin-pwa`, `frontend/vite.config.ts`) deliberately does not cache `/api/` responses — Workbox's Cache API throws on `cache.put()` for non-GET requests, and an unscoped runtime-caching rule previously broke every DELETE/PATCH/POST silently. TanStack Query's own persistence to IndexedDB (via `idb-keyval`, wired up in `main.tsx`) covers the offline/instant-reopen goal instead.
